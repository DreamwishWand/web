## Scope and trust boundaries

- **Client credential candidate (C):** `CommunityLabClient.session` and `getValidSignedSession()` are process-local Auth candidates. `generation`/`logoutEpoch` and tokenless `subscribeSession` fence in-module async work. Cold module **never imports stored v2 Auth**; new tab/reload requires an interactive Auth response. Neither client Session nor local `expiresAt` proves Account owner, Work policy, continued authorization or durable global revocation.
- **Notification plane (N):** `localStorage` notice v2 contains only `{kind:'logout',scope:opaqueConfigScope,nonce}`; native `StorageEvent` is best effort between *participating same-origin running contexts*. It is not an authentication message, cryptographic source, durable message queue, or revocation acknowledgement. A delivered matching notice is a safe **invalidate-only hint**. A missing notice says nothing.
- **Owner UI/controller (U):** PR297 Owner Consumer is compiled OFF. It compares local candidate on Focus/PageShow but **does not perform remote revocation confirmation on lifecycle events**. Accepted PR291 reader has sticky CAS/403 + explicit Fresh requirements. On any session/Work/invalidation event, abort old reads, clear private projections and require an authoritative new response before presenting Owner-verified state; do not bypass sticky CAS with ordinary inspect. `ownerReadVerified`, `actionsEnabled`, `liveBackendEnabled` remain **FALSE** until separate managed acceptance and flags.
- **Authoritative server (S):** signed Source153/GoTrue subject and its DB/RLS/Work/Policy/Consent/OwnerAuthority checks are the ONLY authority for each private read or mutation. A valid-looking locally stored JWT or a successful Auth Refresh is not Work ownership. Real server-side ability to reject a **previously issued, still-unexpired JWT after provider logout, network failure or Account revocation** is **RUNTIME_REQUIRED / UNPROVEN**. A JWT signature/expiry check by itself does NOT establish revocation.
- **Caller trust:** tabs or a same-origin script may send spurious localStorage/BroadcastChannel events. Treat them only as *invalidate* hints, never as proof of login, Work authority, update success or logout completion. Arbitrary same-origin JS compromise is not mitigated by these primitives.

## Required fail-closed Owner authority state machine (contract for a FUTURE separately reviewed implementation)

`UNAUTHENTICATED` → fresh interactive Auth response → `CANDIDATE_UNVERIFIED`. This **never** becomes `OWNER_VERIFIED` because of token expiry, Storage, BroadcastChannel, Focus, local Refresh, a cached DTO or an arbitrary Origin message.

An explicitly authorized Owner Inspect/Read with signed Auth candidate and valid Work locator may ask the **accepted** Source153/strict WEB267 server path for a **fresh server-authoritative assertion**, bound to current actor, Work, PolicyRevision/CAS, Privacy/Consent, session revocation identity/version **where implemented**, and private cache handling. Only a returned, current, valid authoritative response in the same un-aborted client Generation/Work/Actor/Session epoch may produce `OWNER_VERIFIED_READ_ONLY`. Runtime provider JWT validation + revocation freshness must be independently demonstrated. Do not invent a new Source153 field or retrofit privilege from UI metadata.

On ANY logout/local observer event, Account/Work switch, late response, local refresh failure, 401/403, permission mismatch, abnormal lifecycle resume, timeout/unknown server state, or suspect/absent revocation proof: **clear/obscure protected Owner projection, cancel pending work and transition to `AUTHORITY_STALE` or `UNAUTHENTICATED` before showing a private result**. If offline, stay blocked; do not serve a stale private view as owner-verified or enable Writes. When explicitly authorized recheck fails/unavailable, remain `AUTHORITY_STALE` and show neutral status. New valid credential does not clear a sticky CAS403 automatically. Respect PR291 explicit Fresh to reset CAS. A permission revocation requires a new independent server-authoritative check; no action may rely solely on UI-projected `OWNER_VERIFIED` from a prior read.

**Event triggers:** Focus and PageShow (including BFCache), visibility→visible, Online or reconnect, and any explicit owner view resume *must synchronously mark authority freshness UNKNOWN and hide sensitive Owner UI*, then require a new **explicitly authorized** authoritative read before Owner display/action. A trigger may schedule/coalesce a read **only** after a separate user-approved design and exact gate, and must never produce uncontrolled network requests, break PR291 manual Fresh, skip a cache layer or issue a Writer retry. Cold Start stays unsigned (PR294 immutable). Avoid assuming a fresh remote check occurred if no request/verified response exists. Hidden/offline tabs cannot be synchronously notified when all channels fail; server must independently enforce privileged requests.

**Authorization freshness invariant:** for a private action, the server validates the *current* Auth identity/session and every relevant Work/Owner/Policy/Consent/privacy/revocation condition **at action time**; do not rely on a client-held `OWNER_VERIFIED_READ_ONLY` grant or a fixed JWT TTL. Under a transient failure, respond denial/unknown rather than optimistic write. Under 401, **no automatic non-idempotent Writer replay**; read-only query may use the separately accepted bounded retry, but any new server 403/CAS rejects are terminal until explicit Fresh as applicable.

## Minimal channels / delivery semantics

1. **Current primary:** v2 tokenless scoped localStorage `StorageEvent`. Validate schema/scope. Invalidate on matching message. Never put JWT, Refresh Token, Account ID, email, raw publishable key or Work private identifiers in any event/log.
2. **Optional supplement:** `BroadcastChannel` with a versioned, tokenless `kind:'logout'` + opaque config scope + random nonce, **invalidate-only**, never authorize. Experimental real Chrome active-tab delivery can work even when localStorage writes throw; this does **NOT** ensure delivery in sleeping tabs, different browser profiles, restricted browser APIs, old code, or network partitions. Channel listeners and cleanup must be source-reviewed and separately tested before rollout. No sender acknowledgement equals server revocation.
3. **Authoritative plane:** independently signed server OwnerAuthority / current session/Work/Policy checks, plus a **server-enforced revocation epoch/session identity or provider introspection** only after such mechanism is proven in non-Stage116 disposable runtime. A successful GoTrue `logout?scope=local` call alone is NOT proof that every still-valid access JWT will fail the next server request; a failed call cannot be interpreted as revocation.
4. **All notifications fail:** local sender invalidates itself; unrelated active tabs may retain A's candidate. **Only** server-side per-request authorization can prevent backend acceptance; with no deployed/verifiable authority check, the product must keep private OwnerRead and all Writer/Publish/Grant/Delete operations **OFF**. Do not claim forced remote-tab logout.
