## 2. Feasible choices (not yet authorized)

**A — Provider-enforced atomic create-if-absent + independent readback.**
Minimum API-level candidate: Standard Upload with `upsert:false` and a unique never-reused destination key, followed by an entirely separate trusted, authenticated full-byte reader. Official Supabase documentation confirms per-path concurrency for this API only. A viable **product** contract additionally requires *every* S3/REST/TUS/Copy/privileged/Scene/worker route to be incapable of overwriting, renaming, deleting or reusing that key, plus durable origin identity, stale-leases, crash and ACK-loss coverage. Such global immutability is **UNKNOWN**, so A is not accepted. A plain successful upload + second GET cannot prove future immutability when another privileged issuer remains.

**B — Pinned conditional Staging GET → hash/size → unique `upsert:false` Published upload → independent Published reader.**
Best native-Supabase **design candidate**, with these explicit changes to Source137 semantics if ever approved: (1) obtain an exclusive SQL Reservation/Lease Fence for Actor/Account/Creator/RequestHash/expected bytes; (2) use S3 conditional full GET/If-Match only as an opaque source equality guard; stream bounded staging bytes, independently recompute SHA256+exact byte size and validate portable payload; (3) retain *those verified bytes* in the trusted ingress context and upload the same bytes, not a later mutable `Copy` source, to a deterministic collision-resistant never-reused Published Key with `upsert:false`; (4) record upload response but treat timeout/5xx or lost ACK as **outcome unknown**, not negative; (5) independent reader in a distinct trust boundary reads full Published bytes, computes SHA256/Size and returns signed, short-lived, request+key+fence+role+digest-bound evidence; (6) recheck SQL Reservation/Lease/Account/Creator/Privacy/Moderator/graph under existing Source138 all-fence Incident serialization and Source135 candidate semantics; (7) only after new reviewed Provider Attestation authority, immutable writer policy and Gate B signed race acceptance consider a reviewed positive Commit. No such positive authority exists today. `HEAD` alone, client-supplied SHA, ETag==SHA and synthetic `provider_object_version` do not satisfy it. The *Source137 versioned driver remains blocked unchanged* until an explicitly reviewed, separately tested versionless contract exists.

**B cannot provide native WORM merely by upload.** Operator A must close/deploy ALL old Generic/Scene/Retention and any privileged aliases, deny unrelated `UPDATE`/`DELETE` on Published keys, ensure neither a service_role escape nor signed upload path can replace it, audit S3 and direct object APIs, constrain mutable Staging, and verify bytes remain fixed during the entire pre-commit/acknowledgement race. SQL locks cannot atomically fence unrelated Storage API calls. Provider/DB do not have one shared ACID commit; write-then-DB-commit is a fail-closed saga only after orphan/missing-object/quarantine/recovery acceptance.

**C — External truly versioned Object Storage.**
A provider with real immutable version identity, conditional destination creation, version-pinned reads, independently verified bytes, suitable IAM/Object Lock or equivalent, and safe conditional version-targeted cleanup is an **architectural alternative / DESIGN HYPOTHESIS**, not currently configured. Enabling bucket Versioning alone is insufficient: the `latest` pointer can change; commits/readers must pin the immutable version and policy must prohibit dangerous overwrite/delete. A new provider would still require atomic SQL-vs-storage failure handling, ownership/Creator/Privacy/legal/Cloud reference integration, migration/backups and external Gate B.

**D — Fail closed.**
**Current selected decision.** If A/B provider-wide immutability, trustworthy independent attestation and postcommit safety cannot be demonstrated—or external C is not selected—positive publication stays OFF. Preserve staged data/diagnostics and negative incident/new-read suppression; do not promote `EDGE_READBACK_UNATTESTED` to `PROVIDER_ATTESTED`. No Source143 migration or attestor until reviewed Gate B feasibility.

## 3. Required invariant and failure outcomes

- **Namespace:** Generic and distinct Scene must use a *single* Reservation/key authority. Key = Owner/Account/idempotency-bound collision-resistant identity; request hashes and exact bytes pinned; keys are never recycled after unknown outcomes, privacy retirement, aborted attempt or repair. A different request with same key is conflict/quarantine, not an opportunistic blob adoption.
- **Writer inventory:** Published destination must have exactly one authorized create-only channel after Operator A; *all* Copy, S3 Put, direct REST/TUS, Edge aliases, signed upload, privileged SQL metadata or service-role bypass, retention/cleanup worker and operator access need explicit audit. Any unclosed alias -> global block.
- **Lease:** DB Fence/version checked both before and after physical operation. Expired or displaced lease denies SQL Commit even if bytes appeared; object preserved in quarantine. Never assume Storage honors a PostgreSQL Fence.
- **Winner identity:** A successful no-upsert upload never proves the winner belongs to the caller if the ACK was lost. Collision, missing response and HTTP 5xx trigger durable status `OUTCOME_UNKNOWN`, independent full-byte check and operator reconciliation, not overwrite, compensation Remove or automatic success.
- **Independence:** Attestor must not reuse the publishing client's asserted digest, storage metadata, untrusted credential or cached GET. Bind independent observed full bytes/size to reservationID+Owner+key+fence+requestHash+issuer/attestor identity+expiry+nonce; audit replay and issuance. Object bytes require continuous immutability between attestation, SQL Commit and later reads.
- **Commit vs provider:** Source138 Incident veto on **every** previous/current Lease Fence before *both* first commit and completed idempotent replay. Same-key same-intent completed replay only if still non-quarantined and independently reconciled; negative quarantine wins. SQL failure after physical write leaves an orphan, never physically deletes it. After-commit missing/mismatch triggers Source139/140/141/142 incident suppression of *new* supported reads, never mutable rewrite to 'repair'.
- **Physical cleanup:** No version ID or conditional-version delete exists in native Supabase; refuse cleanup, including 72h and all failed Copy/ACK-loss compensations. Gate C requires complete current+historical Preset/Gallery/Scene/Media/Cloud linked-profile/legal/privacy/moderation graph and separate operator authorization. One unknown reference -> DENY.
- **Signed URL/CDN:** New signed issuer/gateway/SQL reads subject to incident guards; already issued token remains independently usable until expiry or cache behavior allows, and in-flight response cannot be retracted. Do not delete objects to emulate token revocation; Gate B separately measures token replay at issue time, 60s, 300s and expiry on cold/warm CDN and browser caches.
