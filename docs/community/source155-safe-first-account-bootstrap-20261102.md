## Concurrency and idempotency

The `provider,subject` unique index, Creator owner unique key and advisory lock make first signup naturally idempotent. Seven concurrent genuine signed requests and a retried request must return identical immutable Account/Creator IDs, exactly one Creator outbox, no role elevation, no duplicate identity. Different handles on a replay do **not** change existing account/profile — this is subject-key idempotency, not client-selected reconfiguration. A handle collision or failed validation must roll back the entire new-account transaction; retry with a free handle must succeed. Role/owner assignments remain account-scoped. A valid sibling Session can continue after a Local terminal revoke; the old or GoTrue refreshed same Session must fail.
