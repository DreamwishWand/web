## Configuration isolation v2 (2026-11-02, new-only follow-up)

**Accepted baseline:** PR294 `2bd20b4ea07c53f413c5d1aa135b2e84d94962e3`. This section records only the subsequent config-scope change, not a re-acceptance of the old ten tests.

- SharedAuth identity remains the normalized HTTPS Supabase URL **and** full publishable key. A deterministic opaque 128-bit routing digest of that pair selects `dreamwishwand-community-session-v2:cfg2-…` in **tab-scoped sessionStorage**. Neither URL nor raw publishable key is included in the storage key or logout notice. The digest is **not a security/authentication proof**; session import additionally requires an exact URL and publishable-key comparison against the persisted v2 envelope.
- The v2 envelope is `{version:2,config:{supabaseUrl,publishableKey},session}`. Unparseable, malformed, foreign-config, or inaccessible Storage yields **no session**. Invalid own-config records are removed on best effort. A hypothetical digest collision cannot cause a foreign-config token to be imported because envelope comparison fails.
- **Legacy migration decision: do not migrate.** `dreamwishwand-community-session-v1` has no authenticated connection provenance. Delete it on new-client initialization, reject it even if syntactically valid, and require interactive sign-in again; there is no attempt to guess origin from JWT claims or migrate based on current URL.
- Logout notices now use `dreamwishwand-community-logout-notice-v2`, `{kind:'logout',scope:'cfg2-…',nonce}`, and only invalidate matching full-config SharedAuth state. Old URL-scoped v1 notices are not treated as v2, avoiding cross-publishable-key logout. Notifications contain no JWT, refresh secret, account ID, email, publishable key, or password. Existing same-config generation fences and single-flight rotation are retained.
- Deterministic new-only synthetic tests cover different URL, same URL/different publishable key, independent sign-in/logout, legacy rejection, malformed/mismatched v2 records, blocked storage, scoped notifications, same-config in-flight sharing, simultaneous A/B rotation and late A response after A logout. These are local mock HTTP and StorageEvent harness checks—not managed multi-tab browser, real GoTrue, real JWT, ingress, or production authorization acceptance.
- Cross-version compatibility with *already-open pages running v1 code* is not guaranteed; deployments remain disabled. Same-origin JavaScript can read sessionStorage under browser origin rules; this change provides **configuration isolation**, not script-injection defense or a substitute for server-side JWT/Work authorization.

**Release boundary:** Draft / DO_NOT_MERGE / DO_NOT_DEPLOY. Production Feature Flags remain OFF. Source153, WEB267, PR290–292, Stage116, Provider, Cloud, Native Writer untouched. Require 04 QR new-only independent review of the follow-up HEAD.


## Storage write-failure fail-closed follow-up — 2026-11-02

**Frozen independently accepted configuration-isolation v2 HEAD:** `a079b5ede3a33791ebf91bc0dcdd8390e4c756d3`. This repair adds only Storage write-denial semantics, one dedicated synthetic negative test file and dedicated CI invocation; accepted 17 historical tests, same-config Single-Flight, cross-config exact URL/key matching, scoped tokenless event format and Writer 401 no-replay remain contractually unchanged.

**Negative behavior:** `saveSession` now returns a success/failure outcome rather than propagating a browser Storage exception. On `setItem` or `removeItem` exception it first tries removal of the original persisted scoped Credential, then a non-Credential `null` tombstone overwrite. Regardless of cleanup outcome it attempts a tokenless `localStorage` quarantine keyed only by the opaque config scope. `commitSession` always advances generation and, when the effective result is unsigned, advances logoutEpoch and notifies subscribers before returning/throwing. Positive Sign-in/Refresh/Account-switch transitions throw generic `SESSION_STORAGE_WRITE_FAILED` after forced in-memory invalidation; Logout and other null-session transitions continue best-effort Provider/cutoff behavior with a tokenless `session-invalidated` notice. Storage exception messages (including user secrets) are never interpolated into observer payloads or surfaced by the new failure code. Same-tab state is invalidated synchronously and late in-flight rotations still fail generation/epoch fences.

**Durable stale snapshot guard:** New-client `loadSession` refuses v2 hydration when an exact-configuration tokenless quarantine exists, when guard localStorage cannot be read, or when probe writes/deletes to either localStorage or scoped sessionStorage fail. Successful later sign-in must durably replace the old v2 snapshot and clear quarantine before memory becomes signed. A failed attempt cannot re-import a stale candidate under the covered persistent write-denial/quarantine cases. The quarantine is a revocation hint, NOT JWT revocation or proof of server-side cutoff; remote server authorization remains mandatory.

**Unavoidable residual:** If both sessionStorage deletion/overwrite AND localStorage quarantine write fail, an already stored credential may remain readable. While writes remain blocked, new-client hydration fails the probes. If **both stores recover after the failed logout and no durable marker was written**, there is no purely local, reliable way to identify the old snapshot as revoked. The repair does **not** claim that an actual server-revoked JWT is invalidated by client Storage, or that a fully blocked browser can persist revocation. Treat this transient all-write-denied + later recovery as **UNRESOLVED / FAIL CLOSED IN CURRENT TAB ONLY** until an externally authoritative session validation/revocation mechanism is proved. Do not infer safe cross-tab behavior if `localStorage` notice writes are also blocked.
