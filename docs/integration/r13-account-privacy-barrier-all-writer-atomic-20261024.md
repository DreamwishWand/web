## A. Durable Privacy Barrier: correct phase boundary

The owner Source \`public.community_request_privacy_suppression_v1\` and compatibility \`public.community_tombstone_account\` now mean **phase 1 account public suppression**, NOT deletion completion. The SQL accepts verified recent session and explicit DELETE, serializes the account request with an account-level advisory and \`wand_accounts FOR UPDATE\`, writes one durable \`private.account_privacy_suppressions\` row (\`suppressed_cleanup_pending\`), removes owner SearchDocuments, inserts one Outbox + Audit event and returns \`fullDeletionComplete=false\`, \`previousBearerUrlsRevoked=false\`, and \`retentionPolicyApproved=false\`.

It MUST NOT mutate published Gallery Works, remove historical PresetRevision references or pretend issued Storage URLs are already revoked. Real physical media/Cloud clean-up, 72-hour TTL, lawful account erasure, archival holds and any recovery path remain independent pending jobs. Public-read suppression is NOT irreversible purge or immediate CDN invalidation.

Read-time enforcement presently relies on the owner's override to \`private.is_discoverable_work\`, \`private.can_access_work\`, Creator public/read RLS, \`community_search_public\`, \`community_get_public_media_storage_v1\` and \`community_gallery_media_gateway_v1\` (those media functions call discoverability), and owner \`resolve_active_account\` denying new writes. Existing direct Storage signed bearer issued before barrier may remain valid through up-to-300s nominal TTL and CDN caches; no current-key revocation was demonstrated. Additional direct read paths, DreamSnaps and private/granted reads need an exhaustive registry and signed QA. Do not infer that all consumers honor the common discoverability helper.

A successful privacy phase must remain retry-idempotent using its dedicated session-bound RPC even when regular account writes are disabled. Failed transaction/lock-timeout must roll back **all** barrier/audit/search/outbox side effects. A genuine signed Owner A/Nonowner B/Moderator M Staging test is still required.

### Explicit transaction sequence

1. **Before** any Artifact/Work/reference lock, resolve actual signed Actor, session/current identity and account privacy epoch. Require real account ownership/Creator or independent moderator authorization. No client-submitted service role as actor. Operation/idempotency key validated prior to mutations.
2. Acquire an Account root lock: owner writers **\`wand_accounts FOR SHARE\`**, account privacy/erasure transition **\`FOR UPDATE\`**, using deterministic account UUID order for multi-owner graphs. This must occur **before other Work locks** at RPC entry. An \`AAA BEFORE UPDATE\` account-lock trigger is only defense-in-depth, cannot substitute for RPC-level ordering because Gallery v4 has already locked GalleryWork before firing Work triggers.
3. Provisional graph reverse-discovery: enumerate ALL direct AssociatedGallery/Artifact, current and historical \`preset_revision_publications\`, \`gallery_revision_presets\`, any Gallery Revision reference, current Media/Cover/Cloud and approved native registry. Include both old/new reference sides, unrelated owners as security-deny, all revision IDs; no silently empty UNKNOWN category.
4. Lock Artifact UUIDs sorted, then PresetWork UUIDs sorted, then GalleryWork UUIDs sorted, one row at a time. After holding locks, re-read account privacy barrier/actor/owner/Creator, Work rowVersions/currentRevision pointers, historical references and full graph SHA version \`ddv.graph-allwriters@r13\`. Stale graph, newly appeared graph node, unexpected Work/owner/Creator/Media, or unknown type **terminal abort**, not successful skip.
5. Exactly once in same DB transaction: immutable Revision/edges, Work pointers/status, Search projection, Outbox, idempotency result and audit. Atomic rollback on every error; new issuer only after commit and reauthorization.
6. Backend client adapter bounded **fresh whole-transaction** retries for SQLSTATE \`40P01\`, \`55P03\`, \`40001\` (proposal max three attempts including first, deadline budget, jitter). Each retry creates a new connection/transaction, reloads token/session/owner/account suppression+graph/idempotency and rechecks expected fingerprint. Never reuse stale successful authorization across attempts. Semantic owner/version/graph mismatch NOT retried automatically.
7. Safety exception: moderator restrict/remove and phase1 account privacy barrier may commit **without** completing optional Gallery/Cloud/Media graph cleanup. Public read/search/media issuance must consult the durable safety state, and positive restore requires complete graph proof.
