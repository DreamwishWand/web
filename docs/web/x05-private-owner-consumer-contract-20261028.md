## Proposed minimal private read DTO (NOT LIVE)

Use contract discriminator `wand.dreamsnaps.private-owner-consumer@1` **only for future negotiation**, not as an existing RPC version. The implemented pure decoder rejects unknown or additional keys, ambiguous types, identity mismatch and URL/signer/storage key fields.

- `work`: `workId` (UUID, the sole URL/work control ID), `ownerAccountId` (same verified signed subject-derived Account), `creatorProfileId` (verified same owner), `kind` (`OriginalCompetition` or `PostEventCreation`), `challengeId` (official-identity binding still unverified), immutable `photoRevisionId` + `mediaId` (opaque database identity, **not** Storage path or bearer access), independent `conceptRevisionId`, optional approved `conceptText` (string or null). Original **requires** real `entryId` and `frozenEntryRevisionId == photoRevisionId`; PostEvent **must omit** both Entry fields. No synthetic rank, award, payment or false event Entry.
- `authority`: ownerAuthorized true backed by **real trusted server verification**, Account and Identity active, retired false, privacySuppressed false, moderationAllowed true, photoBindingVerified true, mediaOwnershipVerified true; current positive safe-integer `rowVersion` and `authorizationEpoch`. Backend must re-evaluate these atomically on every private read/write; a DTO boolean is never browser-side authentication.
- `grant`: `state` accepted/withdrawn, exact opaque **TEXT** `policyIdentifier` (Source149 `grant_policy_version TEXT`), separate integer `consentEventVersion` (Source149 consent-event sequence, <= Work rowVersion), bound `workId`+`mediaId`, affirmative declared self-capture, explicit grant acceptance, exactly store/display/thumbnail/CDN Source149 scopes. The SQL `grant_policy_digest` is a server-only verification input; it does **not** need to traverse to Browser. Legacy WEB245 `imageGrant.policyVersion: positive INTEGER` is **not equivalent** to SQL `grant_policy_version`; do not parse, coerce, alias or silently reuse the earlier decoder. If a future service chooses a numeric presentation revision, it must explicitly specify a different field and semantics. The decoder retains policy identifier `'00003'` without converting it to `3`.
- `deletion`: `controlState` from Source149 consented/preflight_blocked/withdrawn/delete_requested, `publicDisabled` from **authoritative live Work visibility** and read-suppression, `purgeState` exactly not_requested/requested/provider_pending/provider_reported/verified. `providerVerificationAccepted` and `purgeScopeComplete` are additional future Provider/Retention/Cloud service assurances **NOT produced by Source149**. `legalHold` indicates a hold. Only verified + both affirmative authoritative provider/scope assertions + public disabled + no hold may project `MEDIA_PURGED`; Source149 only writes requested and can never prove this. `PUBLIC_DISABLED` must **not** be labeled completed purge; already-issued signed URL/Origin/CDN and third-party downloads are separate runtime/physical concerns.

**Data minimization:** transport may return opaque MediaID to a securely authenticated Owner consumer for integrity matching, but may NOT return Storage Key/bucket/path, signed URL, JWT, provider receipt digest, image bytes, internal AuthSubject or arbitrary public Work Detail. ## Request freshness, CAS and race semantics

1. A future trusted backend (owned by 03 COMM) verifies token/session/issuer and pins `p_auth_subject` **server-side**. All Source149 private `SECURITY DEFINER` functions currently have REVOKE ALL on public/anon/authenticated/service_role and must not be surfaced via browser or arbitrary privileged SQL. New caller needs narrow approved Execute and source-qualified Owner read contract, never a blanket service_role GRANT.
2. Initial authenticated read returns fresh `rowVersion` and `authorizationEpoch` from authoritative locked/snapshot-consistent DB; the *first read* has no client expected version. A subsequent read or mutation compares both with its previously accepted current snapshot. `requestGeneration === latestGeneration` prevents stale SPA navigation/appended response. Client generations are NOT SQL epochs.
3. Mutation requires WorkID + trusted actor + exact `expectedRowVersion`; action must also carry/check `authorizationEpoch` as a revocation fence. Source149 currently only accepts `p_expected_version` in SQL and bumps rowVersion and epoch; trusted wrapper must revalidate epoch/owner/privacy and return authoritative new state. Client must not infer new epoch as `old+1`, nor auto-increment the local rowVersion. Actual idempotency/replay and error mapping require Backend contract.
4. `409/412` or stale epoch -> clear old snapshot and `REFRESH_REQUIRED`; **no optimistic success, automatic retry or stale media**. `401/403/404/410`, inactive Actor, deleted Work, privacy suppressed, no signed session -> `BACKEND_UNAVAILABLE` and clear previous data. Any eventual 2xx action response requires fresh authoritative owner read before exposing success or status. All private HTTP responses `Cache-Control: private, no-store` plus appropriate caller binding/incident-first controls.
5. No client-side processing of already withdrawn grants may re-enable publishing, Media, Search/Creator/Saved/Share or new signer. Revocation outbox in Source149 is not proof that an already issued ~300s bearer or CDN cache has expired.
